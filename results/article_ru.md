# Автоматизация построения признаков в рекомендательных системах: сравнение ручного набора и генерируемого пула из 487 признаков на Yambda-50M

## Аннотация

Исследуется, может ли программный перебор заранее описанного пространства признаков заменить ручной подбор признаков для градиентного бустинга в задаче ранжирования кандидатов. Целевое событие: прослушивание трека не менее чем на 50 % (Listen+) в течение суток после момента прогноза. Данные: Yambda-50M, выборка из 2000 пользователей (9 270 957 событий). Бейзлайн (LightGBM, 134 ручных признака) сравнивается с пулом из 487 признаков, заданных грамматикой «сущность — событие — агрегат — окно». Набор кандидатов, отсечки времени и бюджет подбора гиперпараметров одинаковы для всех вариантов.

На лёгком протоколе кандидатов (3 seed, подбор гиперпараметров) пул превосходит ручной набор: ΔAUC = +0.0055, 95 % ДИ [+0.0038, +0.0072]; ΔNDCG@10 = +0.0068, [+0.0026, +0.0108]. На трудном протоколе (1 seed, параметры по умолчанию) наблюдаются ΔAUC = +0.0060 и ΔNDCG@10 = +0.0144. Отрицательные результаты: жадный отбор семейств признаков не отличим от ручного набора, сетка из 13 окон не отличима от окон 1/7/30/all, затухающие счётчики и тренды не дают прироста сверх пула. Наибольшее снижение AUC при удалении группы признаков наблюдается для признаков связи «пользователь—артист» и «пользователь—трек». Приведены код, тесты на отсутствие утечек и пошаговая инструкция воспроизведения.

### Два протокола кандидатов (кратко)

Модель ранжирует не весь каталог, а список кандидатов в каждой группе (пользователь, отсечка). Кандидаты формируются сэмплированием, и от того, насколько «похожи» отрицательные примеры на положительные, зависит трудность задачи. В работе используются два протокола, различающиеся только составом отрицательных кандидатов (положительные, отсечки и признаки одинаковы):

| | Лёгкий протокол | Трудный протокол |
|---|---|---|
| Отрицательные кандидаты | 20 популярных треков + 20 треков из истории пользователя | 50 популярных + 50 из истории + 50 треков топ-5 артистов пользователя |
| Кандидатов на группу | 55 | 161 |
| Доля положительных | 0.282 | 0.097 |
| Назначение | основной протокол: 3 seed, подбор гиперпараметров, все эксперименты | проверка устойчивости выводов: 1 seed, параметры по умолчанию, сокращённый набор экспериментов |

В трудном протоколе отрицательные чаще относятся к знакомым пользователю артистам (72 % против 59 %), поэтому простой признак «знаком ли артист» различает кандидатов хуже, и задача сложнее. Подробности — в п. 1.4.

## 1. Описание задачи

### 1.1. Постановка

Для пары (пользователь *u*, трек *i*) в момент времени *T* (отсечка) требуется предсказать, будет ли трек прослушан не менее чем на 50 % в интервале [*T*, *T* + Δ), где Δ = 1 сутки. В данных Yambda у прослушивания есть поле `played_ratio_pct` (ρ, доля проигранного трека, %). Прослушивание считается Listen+, если ρ ≥ 50.

Метка:

```math
y(u,i,T) = \mathbb{1}\left[ \exists\, e : \mathrm{user}(e) = u,\; \mathrm{item}(e) = i,\; T \le t_e < T + \Delta,\; \rho_e \ge 50 \right]
```

Признаки *x*(*u*, *i*, *T*) вычисляются только по событиям с *t* < *T*. Это единственное требование, обеспечивающее отсутствие утечки из будущего (см. п. 1.5).

Модель ранжирует не весь каталог, а предварительно сформированный список кандидатов. Этап отбора кандидатов в работе не реализован, поэтому кандидаты формируются сэмплированием (п. 1.4). **Группа** — пара (отсечка, пользователь). В выборку включаются группы, в которых у пользователя есть хотя бы один Listen+ в окне метки и не менее 50 событий истории к моменту *T*.

### 1.2. Метрики

| Метрика | Определение |
|---|---|
| LogLoss | Логарифмическая потеря по всем строкам теста (меньше — лучше). |
| ROC-AUC | По всем строкам теста. |
| NDCG@10 | $`\mathrm{DCG@10}=\sum_{r=1}^{10} y_{(r)}/\log_2(r+1)`$, нормировка на идеальный DCG@10 группы; среднее по группам. |
| Recall@10 | $`\sum_{r=1}^{10} y_{(r)} / n_+`$, где *n*₊ — число положительных в группе; среднее по группам. |

Здесь *y*₍ᵣ₎ — метка трека на позиции *r* в ранжировании модели. В группе в среднем около 15 положительных, поэтому максимум Recall@10 меньше единицы. Метрики на K = 50 не используются: при 55 кандидатах на группу HitRate@50 равен 1.0 для любой модели.

### 1.3. Данные

Yambda — датасет музыкальных рекомендаций Яндекса (лицензия Apache 2.0; описание: arXiv:2505.22238). Вариант 50M: 10 000 пользователей, 934 057 треков, 46.5 млн прослушиваний, 0.88 млн лайков, 0.11 млн дизлайков. Использованы файл `flat/50m/multi_event.parquet` и два отображения «трек → артист» и «трек → альбом».

Из 10 000 пользователей случайно (seed 0) выбрано 2000, история каждого сохранена полностью (обрезка истории занижает счётчики). Выборка содержит 9 270 957 событий. Время в данных глобальное, в пятисекундных бинах, охват — 1505 дней; это проверено скриптом `inspect_data.py`, так как относительное время делает временное разбиение некорректным. Артист известен у всех событий.

Ограничения данных: (а) описание флага `is_organic` на странице датасета неоднозначно (схема и FAQ расходятся в трактовке нуля), поэтому далее используется формулировка «доля событий с флагом 1»; (б) события `unlike` и `undislike` не учитываются, то есть счётчик лайков равен числу нажатий «нравится», а не числу лайкнутых треков на момент *T*.

### 1.4. Протокол оценки

**Отсечки времени.** Для каждой отсечки признаки считаются по всей истории до *T*, метки — по окну [*T*, *T* + 1 сутки). Отсечки образуют три последовательные группы:

- test — последние 3 суток данных, по одной отсечке на сутки;
- val — 3 суток перед test;
- train — 6 отсечек с шагом 3 суток перед val.

Окна меток не пересекаются ни внутри групп, ни между ними (проверяется утверждением в коде и тестом). Признаки, число признаков *k*, гиперпараметры и число деревьев выбираются только по train и val; test используется для итоговых таблиц.

```
время →
 train: [T1]   [T2]   [T3]   [T4]   [T5]   [T6]  | val: [V1][V2][V3] | test: [S1][S2][S3]
 каждая клетка — отсечка T; метка берётся из [T, T+1 сутки);
 признаки — только события до T
```

**Кандидаты.** Положительные — все треки с Listen+ в окне метки пользователя. Отрицательные добавляются из источников:

1. популярные: треки, прослушанные в выборке за 7 дней до *T*; вероятность выбора ∝ (число прослушиваний)^0.75;
2. из истории: случайные треки, ранее прослушанные этим пользователем;
3. из топ-5 артистов (только трудный протокол): треки пяти артистов, прослушиваемых пользователем чаще всего за 30 дней; веса (число прослушиваний)^0.75; выборка без возвращения по схеме Efraimidis–Spirakis.

Треки, оказавшиеся положительными, из отрицательных исключаются. Размеры: лёгкий протокол — 20 + 20, трудный — 50 + 50 + 50.

Трудный протокол введён потому, что на лёгком положительные и отрицательные различимы проще: 70 % положительных — уже прослушанные пользователем треки (среди отрицательных 52 %), 87 % положительных — треки знакомых артистов (среди отрицательных 59 %). В трудном протоколе знакомый артист есть у 72 % отрицательных.

| Характеристика (test) | Лёгкий | Трудный |
|---|---|---|
| Групп | 1257 | 1257 |
| Строк | 69 685 | 202 017 |
| Кандидатов на группу | 55 | 161 |
| Доля положительных | 0.282 | 0.097 |
| Отрицательные — треки знакомых артистов | 59 % | 72 % |
| AUC одиночного признака `ua.listen.cnt.30d` | 0.724 | 0.559 |
| NDCG@10 ручного набора (параметры по умолчанию) | 0.811 | 0.627 |

*Особенность сэмплирования.* Все отрицательные — треки, встречавшиеся в прослушиваниях до *T* (чтобы отрицательные не зависели от будущего). Положительные могут быть треками, которых до *T* не слушал ни один из 2000 пользователей; для таких треков факт появления в списке косвенно указывает на метку. Доля таких треков не измерялась. Абсолютные значения метрик могут быть завышены; влияние на сравнение наборов признаков ожидается меньшим, так как кандидаты одинаковы для всех наборов (это не проверялось отдельно).

### 1.5. Защита от утечек и детерминизм

1. Движок признаков не обращается к событиям с `ts ≥ T`.
2. Тест `tests/test_leakage.py`: признаки, вычисленные на полных данных, совпадают с признаками на данных без событий после *T* (для пула, ручного набора, затухающих счётчиков и трендов). Тест проверен на мутации: при сдвиге *T* на сутки расходятся все признаки.
3. Тест на негативы: каждый отрицательный пример встречался в прослушиваниях до *T* и не пересекается с положительными.
4. Один seed даёт один и тот же список кандидатов в том же порядке. LightGBM запускается в детерминированном режиме; метрики двух независимых запусков в одном окружении совпадают с точностью до 1e-16.

## 2. Подход

### 2.1. Идея

Признаки описываются короткой грамматикой; перебираются все допустимые варианты; результат сравнивается с набором, составленным вручную. Ручной набор входит в пространство перебора как подмножество, поэтому разность метрик отражает эффект расширения пространства, а не использование принципиально других идей.

### 2.2. Ручной бейзлайн (134 признака)

Типичный набор первой версии: счётчики в окнах 1, 7, 30 дней и во всей истории; пять сущностей (пользователь, трек, артист, пары «пользователь—трек» и «пользователь—артист»), четыре вида событий (прослушивание, Listen+, лайк, дизлайк).

| Группа | Число | Состав |
|---|---|---|
| Счётчики | 80 | 5 сущностей × 4 события × 4 окна (1, 7, 30 дней, вся история) |
| Средняя доля прослушивания | 15 | 5 сущностей × 3 окна (7, 30, вся) |
| Конверсия Listen+ / прослушивания | 15 | 5 сущностей × 3 окна |
| Давность последнего события | 8 | дни с последнего прослушивания и последнего Listen+ для пользователя, трека, пар «пользователь—трек» и «пользователь—артист» |
| Лайк-конверсия | 6 | лайки / прослушивания для пользователя, трека, артиста × окна 30 дней и вся история |
| Число уникальных треков | 4 | пользователь и артист × окна 7 и 30 дней |
| Доля пары в прослушиваниях пользователя | 4 | пары «пользователь—трек», «пользователь—артист» × окна 7 и 30 дней |
| Возраст | 2 | дни с первого прослушивания пользователя и трека |

### 2.3. Модель

Для всех наборов используется LightGBM с бинарной потерей. Параметры по умолчанию: learning rate 0.05, 63 листа, `min_data_in_leaf` 50, `feature_fraction` 0.7, `bagging_fraction` 0.8 (`bagging_freq` 1), `lambda_l2` 1. Не более 2000 деревьев; ранняя остановка по LogLoss на val (patience 50). Строки train не взвешиваются.

### 2.4. Грамматика признаков и пул из 487 признаков

Признак задаётся четвёркой `Spec(entity, kind, agg, window)`: «для сущности вычислить агрегат по событиям данного вида за данное окно до *T*». Отношение `Ratio(a, b) = a / (b + 1)` задаёт сглаженную долю.

| Компонент | Значения |
|---|---|
| `entity` | user, item, artist, album, ui, ua, ual (пары «пользователь—трек», «—артист», «—альбом») |
| `kind` | listen, lplus, skip (прослушивание менее 25 %), like, dislike |
| `agg` | cnt, mean_ratio, recency, age, nuniq_item, frac_org |
| `window` | 1, 7, 30, 90 дней, вся история (у recency и age окна нет) |

`frac_org` — доля событий с флагом `is_organic = 1`. Перебираются только допустимые сочетания. Пул: 332 обычных признака и 155 отношений, всего 487. Ручной набор входит в пул (объединение пула и ручного набора также даёт 487 признаков). В ручном наборе отсутствуют: сущности album и ual, окно 90 дней, события skip, агрегат frac_org.

Реализация на Polars: для каждой связки «сущность × окно» история фильтруется один раз (только `ts < T`), оставляются строки, нужные кандидатам, все агрегаты считаются за один `group_by`. Стоимость определяется числом проходов (сущность × окно), а не числом признаков. Если у сущности нет событий, счётчик равен нулю; средние, давность и возраст остаются пропусками.

### 2.5. Стратегии отбора

Все решения принимаются по train и val.

- **Весь пул:** 487 признаков без отбора.
- **Отбор по важности:** модель обучается на всём пуле, признаки упорядочиваются по суммарному gain, перебираются *k* ∈ {25, 50, 100, 200, все}, выбирается *k* с минимальным LogLoss на val. Отдельно фиксируется вариант *k* = 100 («top-100»).
- **Жадный прямой отбор семейств:** семейство — все окна одного `entity.kind.agg`. В шорт-лист входят 40 семейств с наибольшей суммарной важностью; на каждом шаге добавляется семейство с наибольшим приростом AUC на val (прокси-модель: LightGBM, 120 деревьев, не более 300 000 строк train). Остановка при приросте менее 0.0005 или после 15 шагов.

### 2.6. Дополнительные операторы

- **Затухающий счётчик `dcnt<H>`:** вклад события равен 2^(−age/H), age — возраст события в днях, H ∈ {1, 3, 7, 14, 30, 90, 365}. 7 сущностей × 4 события (listen, lplus, like, skip) × 7 полупериодов = 196 признаков.
- **Тренд:** отношение счётчика в коротком окне к счётчику в длинном, пары окон (1, 7), (7, 30), (30, 90). 7 сущностей × 2 события (listen, lplus) × 3 пары = 42 признака.
- **`hand_decay`:** ручной набор, в котором 80 оконных счётчиков заменены на 80 затухающих (полупериоды 1/7/30/365); остальные 54 признака сохранены. Число признаков не меняется (134).

## 3. Эксперименты

### 3.1. Условия сравнения

1. Кандидаты одинаковы для всех наборов признаков (один кэш).
2. Бюджет подбора гиперпараметров одинаков: параметры по умолчанию и шесть случайных конфигураций из сетки `num_leaves` ∈ {15, 31, 63, 127}, `min_data_in_leaf` ∈ {20, 50, 100, 200}, `feature_fraction` ∈ {0.3, 0.5, 0.7, 0.9}, `lambda_l2` ∈ {0, 1, 10}. Конфигурации общие для всех наборов; выбирается минимум LogLoss на val.
3. Ранняя остановка и все решения об отборе признаков используют только train и val.

### 3.2. Оценка неопределённости

Разброс между seed обучения не превышает 0.0003 AUC. Разброс из-за выборки пользователей больше: полуширина доверительных интервалов около 0.0017–0.0024 AUC. Для разности двух моделей строится 95 % процентильный интервал парным bootstrap (Efron, 1979): 300 ресемплов пользователей с возвращением (мультиномиальные веса), одинаковые веса для обеих моделей, метрики пересчитываются по четырём показателям. Ресемплируются пользователи, а не группы, так как группы одного пользователя из разных отсечек коррелированы. Прогнозы перед сравнением усредняются по seed. Поправка на множественные сравнения не вводится; пограничные интервалы (близкие к нулю) следует интерпретировать осторожно. В таблицах жирным выделены интервалы, не содержащие ноль.

### 3.3. Перечень запусков

| Эксперимент | Скрипт | Протокол | Seed | Параметры | Сравниваемые варианты |
|---|---|---|---|---|---|
| Этап 1 | `run_experiments.py` | лёгкий, трудный | 1 | по умолчанию | ручной набор, пул, отбор по важности, жадный отбор (только лёгкий), одиночные признаки |
| Этап 2 | `run_stage2.py` | лёгкий | 3 | подбор (1 + 6) | те же наборы с ДИ; абляции «ручной + группа» |
| Окна | `run_windows.py` | лёгкий | 3 | по умолчанию | ручные окна, сетка из 13 окон, окна по важности, случайные окна |
| Этап 3 | `run_stage3.py` | лёгкий | 2 | по умолчанию | затухание, тренды, top-100, LOGO, время расчёта |
| Этап 3, трудный | `run_stage3.py --quick` | трудный | 1 | по умолчанию | hand, pool, pool + затухание + тренды, top-100; 8 групп LOGO |
| Диагностика | `diagnostics.py` | оба | — | — | повторное потребление, доля знакомых артистов, одиночные признаки |

Трудный протокол проверен слабее лёгкого (один seed, без подбора гиперпараметров, без эксперимента с окнами и без жадного отбора); его результаты следует рассматривать как дополнительное подтверждение, а не основной результат.

### 3.4. Эксперимент по выбору окон

Четыре набора различаются только окнами счётчиков (остальные 54 ручных признака одинаковы):

- **A:** 80 счётчиков в окнах 1/7/30/all (ручной набор).
- **B (сетка):** 5 сущностей × 4 события, окна 1, 2, 3, 5, 7, 10, 14, 21, 30, 60, 90, 180 дней и all: 260 счётчиков, всего 314 признаков.
- **C:** из 260 счётчиков сетки оставлены 80 с наибольшим gain в модели B (бюджет как у A, окна выбраны по данным).
- **R (контроль):** 80 случайных счётчиков из сетки, три выборки.

### 3.5. Leave-one-group-out (LOGO)

Из пула удаляется одна группа признаков (сущность, агрегат, вид события или окно), модель переобучается, вычисляется разность с полным пулом (тот же bootstrap). Чем более отрицательна разность по AUC, тем труднее заменить группу остальными признаками. Группы пересекаются (например, признак входит в ua и в frac_org), поэтому разности не аддитивны. LOGO дополняет абляцию «ручной набор + группа» (п. 4.8).

### 4.9. Ограничения и неподтверждённые результаты

**Не получилось / не подтвердилось:**

- жадный отбор не превзошёл ручной набор (интервалы разности содержат ноль) при затратах 1003 с;
- отбор по важности оставил весь пул (*k* = 487);
- окна, подобранные по данным, и сетка из 13 окон не отличимы от окон 1/7/30/all;
- затухающие счётчики и тренды не дали устойчивого прироста (максимум +0.0009 AUC, пограничный интервал);
- гипотеза об артефакте сэмплирования для frac_org не подтвердилась.

**Ограничения валидности:**

1. *Масштаб.* Использовано 2000 из 10 000 пользователей; статистики треков и артистов вычисляются по выборке. Масштабирование на 5000 и 10 000 пользователей не проверялось.
2. *Кандидаты.* Кандидаты сэмплируются, а не берутся с реального этапа отбора. Доля положительных треков, не встречавшихся до *T*, не измерена; абсолютные метрики могут быть завышены.
3. *Трудный протокол.* Один seed, без подбора гиперпараметров; эксперимент с окнами и жадный отбор не запускались.
4. *LOGO и абляции.* Один seed. Доверительные интервалы учитывают выборку пользователей, но не разброс обучения (около 0.0003 AUC).
5. *Множественные сравнения.* Приведены десятки интервалов по четырём метрикам без поправок; пограничные результаты не следует считать установленными.
6. *Порядок экспериментов.* Тест не использовался при выборе признаков, *k* и гиперпараметров, однако промежуточные тестовые значения наблюдались, и последующие эксперименты (окна, операторы, трудный протокол) спроектированы после них. Возможен небольшой оптимистичный сдвиг оценок.
7. *Объём исследования.* Один датасет, одна цель (Listen+ за сутки), один горизонт, одна модель (LightGBM). В оценку попадают только пользователи с хотя бы одним Listen+ в окне и историей не менее 50 событий.
8. *Данные.* События `unlike` и `undislike` не учитываются; смысл флага `is_organic` неоднозначен.
9. *Отбор.* Жадный отбор использует прокси-модель и AUC на уровне семейств; другие стратегии (например, обратное исключение) не исследовались.
10. *Другие направления* (графовые модели, модели над последовательностью событий) не исследовались; выводы относятся только к перебору признаков и отбору.
11. *Версии библиотек* при основных прогонах в Colab не фиксировались (`requirements.txt` задаёт только нижние границы), поэтому в третьем–четвёртом знаке значения могут отличаться.

## 5. Выводы

1. **Пул против ручного набора.** В равных условиях (одинаковые кандидаты, отсечки и бюджет подбора гиперпараметров) пул из 487 признаков превосходит ручной набор из 134 признаков по всем четырём метрикам на обоих протоколах кандидатов (95 % ДИ не содержат нуля). Лёгкий протокол: ΔAUC +0.0055, ΔNDCG@10 +0.0068. Трудный: ΔAUC +0.0060, ΔNDCG@10 +0.0144 (1 seed, без подбора гиперпараметров). Абсолютная величина прироста невелика.
2. **Способ отбора.** Преимущество дало расширение пространства признаков, а не усложнение поиска: отбор по важности сохранил весь пул, жадный отбор (1003 с) не отличим от ручного набора. Top-100 по важности превосходит ручной набор по AUC и LogLoss на обоих протоколах и в 2.6–3.2 раза быстрее обучается, чем пул; на лёгком протоколе незначительно уступает пулу (ΔAUC −0.0013).
3. **Выбор окон.** При заданной сетке разумных горизонтов точное значение окна влияет слабо: сетка из 13 окон (ΔAUC +0.0006 [−0.0004, +0.0015]) и окна, выбранные по важности, не отличимы от 1/7/30/all. Случайный набор окон хуже (ΔAUC −0.0057 [−0.0071, −0.0042]).
4. **Новые операторы.** Затухающие счётчики и тренды не дают устойчивого прироста (не более +0.0009 AUC, пограничный интервал) при увеличении времени обучения в 1.6–1.9 раза и времени расчёта признаков в 3.3 раза.
5. **Вклад групп.** Наибольшее снижение AUC при удалении наблюдается для признаков связи «пользователь—артист» (ΔAUC −0.0137 на лёгком и −0.0276 на трудном протоколе) и «пользователь—трек» (−0.0133 и −0.0148). Относительная важность групп зависит от способа формирования кандидатов.
6. **Применимость.** Результаты получены на одной выборке данных (2000 пользователей), одной модели и сэмплированных кандидатах; перенос на полный датасет и реальный этап отбора кандидатов не проверялся. Предлагаемые направления: проверка на 5000–10 000 пользователях, на кандидатах реального отбора, доведение трудного протокола до уровня лёгкого (подбор гиперпараметров, несколько seed), сравнение с графовыми моделями и моделями над последовательностью событий.

### 6.1. Окружение

Python 3.10 или выше. Пакеты (`requirements.txt`): `polars>=1.0`, `lightgbm>=4.0`, `scikit-learn`, `pyarrow`, `numpy`, `huggingface_hub`, `pytest`. Основные прогоны выполнены в Google Colab (CPU); версии библиотек там не фиксировались. Проверка кода выполнена позднее в окружении Python 3.13, polars 2.0.0, LightGBM 4.7.0, scikit-learn 1.9.1, numpy 2.5.3: тесты проходят, конвейер работает на синтетических данных; числа на реальных данных в этом окружении не пересчитывались.

Данные загружаются из Hugging Face (`yandex/yambda`) при первом запуске. Если файлы уже имеются, указывается `--data-dir`; требуются `flat/50m/multi_event.parquet`, `artist_item_mapping.parquet`, `album_item_mapping.parquet`.

### 6.3. Полный прогон

Общее время на CPU Colab при 2000 пользователях — по оценке 3–4 часа.

```bash
bash run_all.sh work 2000        # всё подряд

# по шагам (этап 1 запускается первым в каждой рабочей папке:
# остальные скрипты берут из его results.json конфигурацию и наборы признаков)
python run_experiments.py --n-users 2000 --work-dir work     # этап 1 (~30 мин, из них жадный отбор ~17)
python diagnostics.py --work-dir work
python run_stage2.py --work-dir work --seeds 3 --tune 6      # этап 2 (~40 мин)
python run_windows.py --work-dir work --seeds 3              # окна (~10 мин)
python run_stage3.py --work-dir work --seeds 2               # этап 3 (~60–70 мин)
python summarize.py --work-dirs work                         # таблицы -> work/summary.md

# трудный протокол кандидатов (161 кандидат на группу)
python run_experiments.py --n-users 2000 --work-dir work_hard \
       --neg-pop 50 --neg-hist 50 --neg-art 50 --skip-greedy
python diagnostics.py --work-dir work_hard
python run_stage3.py --work-dir work_hard --seeds 1 --quick --skip-timing
python summarize.py --work-dirs work work_hard
```

Кэш признаков: `work*/<tag>[__win|__ext]/*.parquet`. При изменении конфигурации кэш следует удалить; у `run_experiments.py` есть также флаг `--rebuild`. `summarize.py` собирает таблицы из JSON-файлов в `summary.md`, исключая ручной перенос чисел.

### 6.6. Приложение: параметры и форматы результатов

| Параметр | Значение |
|---|---|
| LightGBM, по умолчанию | `objective=binary`, `metric=binary_logloss`, `learning_rate=0.05`, `num_leaves=63`, `min_data_in_leaf=50`, `feature_fraction=0.7`, `bagging_fraction=0.8`, `bagging_freq=1`, `lambda_l2=1.0`, `deterministic=True`, `force_row_wise=True` |
| Длина обучения | до 2000 деревьев, ранняя остановка 50 раундов по LogLoss на val |
| Прокси-модель жадного отбора | `learning_rate=0.1`, `num_leaves=31`, `min_data_in_leaf=50`, `feature_fraction=0.8`, bagging 0.8, 120 деревьев, до 300 000 строк train; 40 семейств в шорт-листе, не более 15 шагов, минимальный прирост AUC 0.0005 |
| Сетка подбора | `num_leaves` {15, 31, 63, 127}, `min_data_in_leaf` {20, 50, 100, 200}, `feature_fraction` {0.3, 0.5, 0.7, 0.9}, `lambda_l2` {0, 1, 10}; 6 случайных конфигураций + параметры по умолчанию |
| Конфигурация данных | `n_users=2000`, seed 0, горизонт 1 день, 6 train-отсечек с шагом 3 дня, 3 val, 3 test, порог Listen+ 50 %, `min_hist_events=50` |
| Кандидаты | популярные: окно 7 дней, вес count^0.75; артисты: топ-5 за 30 дней, вес count^0.75; лёгкий протокол 20/20/0, трудный 50/50/50 |
| Bootstrap | 300 ресемплов пользователей, 95 % процентильный интервал, seed 0 |
| Seed обучения | 0, 1, 2 (число задаётся флагом `--seeds`) |

Результаты каждого скрипта записываются в JSON в рабочей папке (у синтетических прогонов — суффикс `_syn`): `results.json` (`cfg`, `n_pool`, `n_hand`, `feature_seconds_total`, `baseline_hand`, `heuristics`, `auto_importance`, `auto_greedy`), `results_stage2.json` (`methods`, `bootstrap_test_vs_hand`, `ablation`), `results_windows.json` (`methods`, `gain_by_window`, `gain_by_family`, `chosen_windows_C`, `bootstrap_vs_A`), `results_stage3.json` (`methods`, `bootstrap`, `logo`, `timing`, `feature_seconds_build`). В `methods` метрики имеют вид пары [среднее, разброс по seed], в блоках `bootstrap` — словарь `{diff, lo, hi, p_better}`.
