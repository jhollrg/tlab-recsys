## Аннотация

Работа проверяет, может ли программный перебор заранее описанного пространства признаков заменить ручной подбор признаков для градиентного бустинга. Бейзлайн с LightGBM, 134 ручных признака, сравнивается с пулом из 487 признаков, заданных грамматикой «сущность - событие - агрегат - окно». Набор кандидатов, отсечки времени и бюджет подбора гиперпараметров одинаковы для всех вариантов.

Поскольку модель ранжирует не весь каталог, а список кандидатов в каждой группе, кандидаты формулируются в свою очередь сэмплированием, было выбрано разделение на два протокола - легкий и тяжелый, при лёгком протоколе кандидатов (3 seed, подбор гиперпараметров) пул превосходит ручной набор: ΔAUC = +0.0055, 95 % ДИ [+0.0038, +0.0072]; ΔNDCG@10 = +0.0068, [+0.0026, +0.0108]. На трудном протоколе (1 seed, параметры по умолчанию) наблюдаются ΔAUC = +0.0060 и ΔNDCG@10 = +0.0144. Отрицательные результаты: жадный отбор семейств признаков не отличим от ручного набора, сетка из 13 окон не отличима от окон 1/7/30/all, затухающие счётчики и тренды не дают прироста сверх пула. Наибольшее снижение AUC при удалении группы признаков наблюдается для признаков связи «пользователь—артист» и «пользователь—трек». Приведены код, тесты на отсутствие утечек и пошаговая инструкция воспроизведения. Автоматическая генерация и отбор признаков для рекомендательной системы (Yambda-50M).
Важное ограничение результата: кандидаты формируются сэмплированием, и один из способов сэмплирования создаёт косвенную утечку метки через состав списка (раздел 2.7), поэтому абсолютные значения метрик следует читать осторожно.

## 1. Описание задачи
 
### 1.1. Постановка
 
Для пары (пользователь *u*, трек *i*) в момент времени *T* (отсечка) требуется предсказать, будет ли трек прослушан не менее чем на 50 % в интервале [*T*, *T* + Δ), где Δ = 1 сутки. В данных Yambda у прослушивания есть поле `played_ratio_pct` (ρ, доля проигранного трека, %). Прослушивание считается Listen+, если ρ >= 50.
 
Метка:
 
y(u, i, T) = 𝟙[∃ e: user(e) = u, item(e) = i, T ≤ tₑ < T + Δ, ρₑ ≥ 50]

Признаки *x*(*u*, *i*, *T*) вычисляются только по событиям с *t* < *T*. Это единственное требование, обеспечивающее отсутствие утечки из будущего (см. п. 1.5).
 
Модель ранжирует не весь каталог, а предварительно сформированный список кандидатов. Этап отбора кандидатов в работе не реализован, поэтому кандидаты формируются сэмплированием (п. 1.4). **Группа** - пара (отсечка, пользователь). В выборку включаются группы, в которых у пользователя есть хотя бы один Listen+ в окне метки и не менее 50 событий истории к моменту *T*.

### 1.2. Метрики
 
| Метрика | Определение |
|---|---|
| LogLoss | Логарифмическая потеря по всем строкам теста (меньше — лучше). |
| ROC-AUC | По всем строкам теста. |
| NDCG@10 | DCG@10 = ∑ᵣ₌₁¹⁰ y₍ᵣ₎ / log₂(r + 1), нормировка на идеальный DCG@10 группы; среднее по группам. |
| Recall@10 | (∑ᵣ₌₁¹⁰ y₍ᵣ₎) / n₊, где *n*₊ — число положительных в группе; среднее по группам. |
 
Здесь *y*₍ᵣ₎ - метка трека на позиции *r* в ранжировании модели. В группе в среднем около 15 положительных, поэтому максимум Recall@10 меньше единицы. Метрики на K = 50 не используются: при 55 кандидатах на группу HitRate@50 равен 1.0 для любой модели.


### 1.3. Данные
 
Yambda - датасет музыкальных рекомендаций Яндекса (arXiv:2505.22238). Выбран вариант 50M на 10 000 пользователей, обусловленный аппаратными ограничениями. Использованы `flat/50m/multi_event.parquet` и два отображения "трек-артист" и "трек-альбом".
 
Из 10 000 пользователей случайно (seed=0) выбрано 2000, история каждого сохранена полностью (обрезка истории занижает счётчики). Выборка содержит 9 270 957 событий. Время в данных глобальное, в пятисекундных бинах, охват - 1505 дней, это проверено скриптом `inspect_data.py`, так как относительное время делает временное разбиение некорректным. Артист известен у всех событий.
 
Ограничения данных - а) описание флага `is_organic` на странице датасета неоднозначно (схема и FAQ расходятся в трактовке нуля), поэтому далее используется формулировка «доля событий с флагом 1»; б) события "unlike" и "undislike" не учитываются, то есть счётчик лайков равен числу нажатий "нравится", а не числу лайкнутых треков на момент *T*.


### 1.4. Протокол оценки

**Отсечки времени.** Для каждой отсечки признаки считаются по всей истории до *T*, метки — по окну [*T*, *T* + 1 сутки). Отсечки образуют три последовательные группы:

- test — последние 3 суток данных, по одной отсечке на сутки;
- val — 3 суток перед test;
- train — 6 отсечек с шагом 3 суток перед val.

Окна меток не пересекаются ни внутри групп, ни между ними (проверяется утверждением в коде и тестом). Признаки, число признаков *k*, гиперпараметры и число деревьев выбираются только по train и val; test используется для итоговых таблиц.

*Кандидаты.* Положительные - все треки с Listen+ в окне метки пользователя. Отрицательные добавляются из источников:

1. популярные: треки, прослушанные в выборке за 7 дней до *T*; вероятность выбора ∝ (число прослушиваний)^0.75;
2. из истории: случайные треки, ранее прослушанные этим пользователем;
3. из топ-5 артистов (только трудный протокол): треки пяти артистов, прослушиваемых пользователем чаще всего за 30 дней; веса (число прослушиваний)^0.75; выборка без возвращения по схеме Efraimidis–Spirakis.

Треки, оказавшиеся положительными, из отрицательных исключаются. Размеры: лёгкий протокол — 20 + 20, трудный — 50 + 50 + 50.

Трудный протокол введён потому, что на лёгком положительные и отрицательные различимы проще: 70 % положительных — уже прослушанные пользователем треки (среди отрицательных 52 %), 87 % положительных — треки знакомых артистов (среди отрицательных 59 %). В трудном протоколе знакомый артист есть у 72 % отрицательных.

| Строк | 69 685 | 202 017 |

*Особенность сэмплирования.* Все отрицательные — треки, встречавшиеся в прослушиваниях до *T* (чтобы отрицательные не зависели от будущего). Положительные могут быть треками, которых до *T* не слушал ни один из 2000 пользователей; для таких треков факт появления в списке косвенно указывает на метку. Доля таких треков не измерялась. Абсолютные значения метрик могут быть завышены; влияние на сравнение наборов признаков ожидается меньшим, так как кандидаты одинаковы для всех наборов (это не проверялось отдельно).

### 1.5. Защита от утечек и детерминизм

Движок признаков не обращается к событиям с `ts ≥ T`.
Тест `tests/test_leakage.py`: признаки, вычисленные на полных данных, совпадают с признаками на данных без событий после *T* (для пула, ручного набора, затухающих счётчиков и трендов). Тест проверен на мутации: при сдвиге *T* на сутки расходятся все признаки.
Тест на негативы: каждый отрицательный пример встречался в прослушиваниях до *T* и не пересекается с положительными.
Один seed даёт один и тот же список кандидатов в том же порядке. LightGBM запускается в детерминированном режиме; метрики двух независимых запусков в одном окружении совпадают с точностью до 1e-16.


Ограничение способа сэмплирования: косвенная утечка метки через состав списка.

Признаки не содержат информации из будущего, но сам способ формирования списка кандидатов содержит асимметрию, зависящую от метки. Все отрицательные кандидаты обязательно встречались в прослушиваниях до T: популярные берутся из прослушиваний за 7 дней до T, исторические из прошлой истории пользователя, треки топ-артистов из прослушиваний за 30 дней до T. Положительные же определяются только окном метки и ничем не ограничены. Положительным может оказаться трек, которого до T не слушал ни один из 2000 пользователей выборки (выбрано 2000 пользователей из 10 000, поэтому такие треки возможны). Для него все счётчики трека равны нулю, а давность и возраст пропущены, тогда как у каждого отрицательного кандидата счётчик трека не меньше единицы. Условие «трек никому не известен до T» поэтому на 100% указывает на положительный класс, и деревья могут им воспользоваться через счётчики трека, которые есть и в ручном, и в автоматическом наборе. Это не утечка будущего в признаках, а смещение отбора кандидатов, но оно может завышать AUC и NDCG@10, и в реальной системе такого сигнала не будет, потому что кандидатов даёт другой этап.

Доля таких положительных на реальных данных не измерена: реальные данные в среде, где писался этот отчёт, недоступны, а прогоны на них выполнялись в Colab.

## 2. Подход

### 2.1. Идея

Признаки описываются короткой грамматикой; перебираются все допустимые варианты; результат сравнивается с набором, составленным вручную. Ручной набор входит в пространство перебора как подмножество, поэтому разность метрик отражает эффект расширения пространства, а не использование принципиально других идей.

### 2.2. Ручной бейзлайн (134 признака)

Типичный набор первой версии: счётчики в окнах 1, 7, 30 дней и во всей истории; пять сущностей (пользователь, трек, артист, пары «пользователь—трек» и «пользователь—артист»), четыре вида событий (прослушивание, Listen+, лайк, дизлайк).

| Группа | Число | Состав |
|---|---|---|
| Счётчики | 80 | 5 сущностей × 4 события × 4 окна (1, 7, 30 дней, вся история) |
| Средняя доля прослушивания | 15 | 5 сущностей × 3 окна (7, 30, вся) |
| Конверсия Listen+ / прослушивания | 15 | 5 сущностей × 3 окна |
| Давность последнего события | 8 | дни с последнего прослушивания и последнего Listen+ для пользователя, трека, пар «пользователь—трек» и «пользователь—артист» |
| Лайк-конверсия | 6 | лайки / прослушивания для пользователя, трека, артиста × окна 30 дней и вся история |
| Число уникальных треков | 4 | пользователь и артист × окна 7 и 30 дней |
| Доля пары в прослушиваниях пользователя | 4 | пары «пользователь—трек», «пользователь—артист» × окна 7 и 30 дней |
| Возраст | 2 | дни с первого прослушивания пользователя и трека |

### 2.3. Модель

Для всех наборов используется LightGBM с бинарной потерей. Параметры по умолчанию: learning rate 0.05, 63 листа, `min_data_in_leaf` 50, `feature_fraction` 0.7, `bagging_fraction` 0.8 (`bagging_freq` 1), `lambda_l2` 1. Не более 2000 деревьев; ранняя остановка по LogLoss на val (patience 50). Строки train не взвешиваются.

### 2.4. Грамматика признаков и пул из 487 признаков

Признак задаётся четвёркой `Spec(entity, kind, agg, window)`: «для сущности вычислить агрегат по событиям данного вида за данное окно до *T*». Отношение `Ratio(a, b) = a / (b + 1)` задаёт сглаженную долю.

| Компонент | Значения |
|---|---|
| `entity` | user, item, artist, album, ui, ua, ual (пары «пользователь—трек», «—артист», «—альбом») |
| `kind` | listen, lplus, skip (прослушивание менее 25 %), like, dislike |
| `agg` | cnt, mean_ratio, recency, age, nuniq_item, frac_org |
| `window` | 1, 7, 30, 90 дней, вся история (у recency и age окна нет) |

`frac_org` — доля событий с флагом `is_organic = 1`. Перебираются только допустимые сочетания. Пул: 332 обычных признака и 155 отношений, всего 487. Ручной набор входит в пул (объединение пула и ручного набора также даёт 487 признаков). В ручном наборе отсутствуют: сущности album и ual, окно 90 дней, события skip, агрегат frac_org.

Реализация на Polars: для каждой связки «сущность × окно» история фильтруется один раз (только `ts < T`), оставляются строки, нужные кандидатам, все агрегаты считаются за один `group_by`. Стоимость определяется числом проходов (сущность × окно), а не числом признаков. Если у сущности нет событий, счётчик равен нулю; средние, давность и возраст остаются пропусками.

### 2.5. Стратегии отбора

Все решения принимаются по train и val.

- **Весь пул:** 487 признаков без отбора.
- **Отбор по важности:** модель обучается на всём пуле, признаки упорядочиваются по суммарному gain, перебираются *k* ∈ {25, 50, 100, 200, все}, выбирается *k* с минимальным LogLoss на val. Отдельно фиксируется вариант *k* = 100 («top-100»).
- **Жадный прямой отбор семейств:** семейство — все окна одного `entity.kind.agg`. В шорт-лист входят 40 семейств с наибольшей суммарной важностью; на каждом шаге добавляется семейство с наибольшим приростом AUC на val (прокси-модель: LightGBM, 120 деревьев, не более 300 000 строк train). Остановка при приросте менее 0.0005 или после 15 шагов.

### 2.6. Дополнительные операторы

- **Затухающий счётчик `dcnt<H>`:** вклад события равен 2^(−age/H), age — возраст события в днях, H ∈ {1, 3, 7, 14, 30, 90, 365}. 7 сущностей × 4 события (listen, lplus, like, skip) × 7 полупериодов = 196 признаков.
- **Тренд:** отношение счётчика в коротком окне к счётчику в длинном, пары окон (1, 7), (7, 30), (30, 90). 7 сущностей × 2 события (listen, lplus) × 3 пары = 42 признака.
- **`hand_decay`:** ручной набор, в котором 80 оконных счётчиков заменены на 80 затухающих (полупериоды 1/7/30/365); остальные 54 признака сохранены. Число признаков не меняется (134).

## 3. Эксперименты

### 3.1. Условия сравнения

1. Кандидаты одинаковы для всех наборов признаков (один кэш).
2. Бюджет подбора гиперпараметров одинаков: параметры по умолчанию и шесть случайных конфигураций из сетки `num_leaves` ∈ {15, 31, 63, 127}, `min_data_in_leaf` ∈ {20, 50, 100, 200}, `feature_fraction` ∈ {0.3, 0.5, 0.7, 0.9}, `lambda_l2` ∈ {0, 1, 10}. Конфигурации общие для всех наборов; выбирается минимум LogLoss на val.
3. Ранняя остановка и все решения об отборе признаков используют только train и val.

### 3.2. Оценка неопределённости
 
Разности между наборами признаков в этой работе имеют порядок 0.005 AUC, поэтому вывод «набор А лучше набора Б» имеет смысл, только если известно, насколько меняется такая разность при повторении эксперимента. В эксперименте есть несколько независимых источников шума, и разные приёмы покрывают разные из них.
 
**Случайность обучения.** LightGBM на каждом раунде берёт 80 % строк и 70 % признаков на дерево, поэтому запуски с разным начальным значением генератора (seed) дают разные деревья, а ранняя остановка по val выбирает разное число деревьев: у настроенного ручного набора это 257, 320 и 260 деревьев на трёх запусках, у пула 169, 169 и 134. Разброс метрик между запусками измерен по 2-3 запускам (стандартное отклонение по запускам): по AUC он составляет от 0.0001 до 0.0005, то есть на порядок меньше эффектов, о которых идёт речь, но с двумя-тремя запусками эта оценка грубая. Чтобы снизить влияние такого шума на сравнение, прогнозы на тесте перед сравнением усредняются по запускам (получается небольшой ансамбль одинаковых по структуре моделей). Поэтому разности в таблицах с доверительными интервалами (ДИ) немного отличаются от разностей средних значений в таблицах с метриками: например, у пула и ручного набора по AUC это +0.0055 и +0.0051.
 
**Выборка пользователей.** Основной источник неопределённости: тест состоит из 1257 групп, которые принадлежат ограниченному числу пользователей, и другой набор пользователей дал бы другие значения метрик. Для его оценки используется парный бутстрап по пользователям. На каждом из 300 ресемплов каждому пользователю приписывается целочисленный вес (число раз, которое он попал в выборку; веса мультиномиальные и в сумме дают число пользователей), все строки и группы пользователя получают этот вес. AUC и LogLoss пересчитываются со взвешенными строками. NDCG@10 и Recall@10 считаются по группам, поэтому для каждого пользователя заранее суммируются метрики его групп и число групп, а на ресемпле берётся отношение взвешенных сумм. Один и тот же набор весов применяется ко всем сравниваемым моделям (парность): общая часть вариации, которая связана с тем, что одни пользователи просто легче предсказываются, сокращается при вычитании, поэтому интервалы разностей ожидаемо уже, чем интервалы для самих метрик (ширина последних не вычислялась). Доверительный интервал разности это 2.5-й и 97.5-й процентили 300 значений разности; дополнительно сохраняется доля ресемплов, в которых модель лучше базы. Единицей ресемплирования выбраны пользователи, а не группы, потому что группы одного пользователя из разных отсечек коррелированы, и ресемплирование групп занизило бы ширину интервалов.
 
**Что интервал не покрывает.** Доверительный интервал относится к фиксированным обученным моделям и фиксированным спискам кандидатов. Он не учитывает, что отрицательные кандидаты были сэмплированы один раз и могли бы быть другими, что тест охватывает всего три дня, что обучение даёт разный результат на разных запусках (оно учтено только усреднением и разбросом выше) и что подбор гиперпараметров на val тоже зашумлён. Выборка пользователей одна и та же для train, val и test, потому что разбиение идёт по времени, а не по пользователям: интервал отвечает на вопрос «что будет с теми же пользователями в другие дни», а не «что будет с новыми пользователями», и вторая постановка в работе не проверялась.
 
**Как читать интервалы.** Жирным в таблицах выделены интервалы без нуля. При 300 ресемплах каждый из двух хвостов оценивается примерно по семи значениям, поэтому границы интервала шумят, и результаты, где граница отстоит от нуля менее чем на 0.0002 (например, +0.0009 [+0.0001, +0.0016] для затухания с трендами или минус 0.0009 [минус 0.0017, минус 0.00004] для отношений в LOGO), следует считать пограничными, а не установленными. Поправка на множественные сравнения не вводится: в работе несколько десятков интервалов по четырём метрикам, которые между собой коррелированы, поэтому согласованность знака по нескольким метрикам и по двум протоколам важнее, чем наличие нуля в одном конкретном интервале.
 
**Проверка на val.** Косвенная проверка, что выбор по val не привёл к подгонке: порядок наборов на val тот же, что на тесте (AUC 0.9054 у ручного набора, 0.9065 у жадного отбора и 0.9102 у пула), а разность пула и ручного набора на val (+0.0048 по AUC) близка к тестовой (+0.0051). LogLoss на val заметно ниже, чем на тесте (0.3195 против 0.3341 у ручного набора), то есть дни val и test различаются по свойствам; причина не исследовалась, но сравнение наборов от этого не меняется.

### 3.4. Эксперимент по выбору окон

Окна счётчиков (1, 7, 30 дней и вся история) в ручном наборе выбраны по привычке: за ними нет проверки, что именно такие горизонты лучше соседних. Проверить это прямым перебором одного окна нельзя, потому что признаков с разными окнами много, и они сильно коррелируют друг с другом. Поэтому вопрос ставится как сравнение способов выбора окон при одинаковом остальном: меняется только то, какие окна есть у счётчиков, а все остальные признаки, модель, кандидаты и гиперпараметры остаются теми же (скрипт run_windows.py).

Что именно меняется. Из 134 ручных признаков 80 это счётчики событий (5 сущностей × 4 вида события × 4 окна), остальные 54 признака (средние доли, конверсии, давность, число уникальных треков, возраст) во всех вариантах одинаковы. Окно счётчика реализовано как условие T - w * сутки <= ts < T на журнал событий, а «вся история» означает отсутствие нижней границы. В эксперименте участвуют четыре варианта набора счётчиков.

Вариант A - ручной: 80 счётчиков с окнами 1, 7, 30 дней и вся история, то есть исходный базовый набор. Вариант B - сетка: для пяти сущностей (пользователь, трек, артист, пары пользователь-трек и пользователь-артист) и четырёх событий (прослушивание, Listen+, лайк, дизлайк) строятся счётчики во всех 13 окнах: 1, 2, 3, 5, 7, 10, 14, 21, 30, 60, 90, 180 дней и вся история, то есть 5 × 4 × 13 = 260 счётчиков вместо 80, всего 314 признаков. B показывает, что даёт модели возможность выбирать из густой сетки горизонтов, пусть и ценой более чем трёхкратного числа счётчиков.

Вариант C - окна, выбранные данными при том же бюджете, что у A. Модель обучается на всех 314 признаках набора B (параметры по умолчанию, одно начальное значение генератора, ранняя остановка по val), признаки ранжируются по суммарному вкладу в уменьшение потерь (gain), и из 260 счётчиков оставляются 80 лучших. Бюджет в 80 счётчиков совпадает с ручным, поэтому C отвечает на вопрос, выберет ли алгоритм окна лучше, чем человек, если у обоих одинаково много признаков. Важно, что отбор использует только train и val: test в выборе окон не участвует. Вариант R - контроль: 80 счётчиков выбираются из 260 случайно без возвращения (три независимые выборки). Он нужен, чтобы отличить две ситуации, которые без него не различить. Если A, B и C одинаковы, то либо окна действительно не важны, и тогда любой набор счётчиков даст то же качество, либо мы просто не умеем замечать разницу. Случайный набор при том же числе признаков показывает, что любой выбор из сетки так хорош не бывает.

Как читать результат. Эксперимент устроен как проверка трёх гипотез. Если B лучше A, то ручные окна упускают горизонты, и густая сетка помогает. Если C лучше A при том же бюджете, то данные выбирают окна лучше человека. Если R хуже A, то выбор окон всё же имеет значение. Сравнение проводится парным бутстрапом по пользователям (п. 3.2), в качестве базы взят набор A; для R бутстрап построен только для первой из трёх случайных выборок, а в таблице по R приведены среднее и разброс по всем трём. Дополнительно по модели B считается доля суммарного gain, приходящаяся на каждое из 13 окон (в сумме по окнам один), и на каждую пару «сущность.событие»; она показывает, какие горизонты модель реально использует, но не доказывает их причинную роль: gain зависит от числа разбиений по признаку, и непрерывные признаки с большим разбросом значений, например счётчики за длинные окна, могут получать его больше (это возможное смещение мы не проверяли).

Отдельно проверен вопрос «окна или затухание»: набор hand_decay заменяет те же 80 оконных счётчиков на 80 затухающих с полупериодами 1, 7, 30 и 365 дней. Он сравнивается с hand (п. 2.6), число признаков в обоих наборах равно 134.

### 3.5. Leave-one-group-out (LOGO)

### 3.5. Вклад групп признаков: leave-one-group-out (LOGO)
 
**Что требовалось выяснить.** Прирост автоматического набора над ручным показывает, что признаков стало лучше, но не отвечает на вопрос, какие именно признаки дали прирост. Простой способ состоит в том, чтобы добавлять группы признаков к ручному набору по одной и смотреть прирост метрик. В этой работе он был выполнен (абляция «ручной набор + группа», п. 4.8) и оказался ненадёжным: группы признаков в пуле сильно перекрываются, и прирост группы зависит от того, с чем её сравнивают. Сумма отдельных приростов девяти групп примерно вдвое больше прироста всего пула, то есть группы повторяют информацию друг друга. Поэтому основной метод - обратный: из полного пула удаляется одна группа, и модель обучается заново.
 
**Как устроена процедура.** Группа задаётся предикатом над описанием признака (`Spec`): по сущности, виду события, агрегату или окну. Для отношения `Ratio(a, b)` принадлежность группе определяется по числителю a. Это означает, например, что отношение числа Listen+ пары пользователь-артист к числу её прослушиваний (с поправкой +1 в знаменателе) целиком входит в группу ua, даже если знаменатель относится к другой группе. Из пула удаляются все признаки группы, остальные подаются в LightGBM с теми же параметрами по умолчанию и тем же начальным значением генератора, что и для полного пула; ранняя остановка выбирает число деревьев независимо для каждой модели по LogLoss на val. Предсказания на тесте сравниваются с предсказаниями полного пула парным бутстрапом: на каждом из 300 ресемплов пользователей считаются все четыре метрики обеих моделей, а доверительный интервал разности - это 2.5-й и 97.5-й процентили.
 
В скрипте `run_stage3.py` определены 14 групп: сущности ui, ua, ual, user, item, объединение artist и album, окно 90 дней, события skip, агрегаты frac_org, recency и age (вместе), nuniq_item, отношения, а также два разбиения frac_org (органичность пользователя и пар против органичности трека, артиста и альбома), введённые для проверки гипотезы об артефакте сэмплирования. На трудном протоколе по соображениям времени запускается сокращённый набор из восьми групп.
 
| Группа | Правило отбора признаков |
|---|---|
| ua, ui, ual, user, item | сущность признака (для отношений - сущность числителя) |
| artist + album | сущность artist или album |
| окно 90 дней | окно равно 90 дням |
| события skip | вид события skip |
| frac_org | агрегат frac_org |
| frac_org (пользователь и пары) | frac_org с сущностью user, ui, ua или ual |
| frac_org (трек, артист, альбом) | frac_org с сущностью item, artist или album |
| recency + age | агрегат recency или age |
| nuniq_item | агрегат nuniq_item |
| отношения (rate) | любой признак типа `Ratio` |
 
**Что измеряет этот метод и чего не измеряет.** Разность с полным пулом показывает не полезность группы вообще, а её незаменимость: если другие признаки несут ту же информацию, удаление группы почти не меняет качество, и метод недооценит её важность. Поэтому малые значения (например, для окна 90 дней или отношений) нельзя читать как «признаки бесполезны», а крупные падения (ua, ui, item) означают, что остальные группы эту информацию не повторяют. Группы пересекаются (признак может входить и в ua, и в frac_org), поэтому падения разных групп нельзя складывать. Все удаления выполнены на одном запуске обучения, поэтому доверительные интервалы отражают разброс из-за выборки пользователей, но не разброс самого обучения (по нашим данным до 0.0003 AUC), и эффекты порядка 0.001 AUC близки к этому уровню шума.

### 4.2. Отбор признаков
 
Отбор по важности пробует пять размеров набора и на val даёт следующие значения LogLoss и AUC: для 25 признаков 0.3300 и 0.8964, для 50 признаков 0.3255 и 0.8999, для 100 признаков 0.3134 и 0.9095, для 200 признаков 0.3141 и 0.9091, для всех 487 признаков 0.3133 и 0.9097. Качество растёт до 100 признаков и дальше почти не меняется, а выбор k = 487 вместо k = 100 основан на разнице в 0.0001 по LogLoss, то есть фактически на ничьей. Поэтому вывод «отбор сохранил весь пул» не означает, что нужны все 487 признаков: он означает, что к 100 признакам по важности остальные добавляют очень мало, и именно это подтверждает вариант top-100 (таблица 3).
 
Жадный отбор семейств завершился после 12 шагов (допускалось до 15, порог прироста 0.0005) и выбрал 12 семейств, то есть 52 признака. Качество упрощённой модели на val растёт так: после первого семейства (средняя доля прослушивания пары пользователь-артист) AUC 0.796, после второго (счётчики трека) 0.844, после третьего (счётчики пары пользователь-трек) 0.882, затем каждое новое семейство добавляет от 0.0006 до 0.006, и итоговое значение составляет 0.9052, что сопоставимо с ручным набором (0.9054 на val у его полной модели). Иначе говоря, три первых семейства дают основную часть качества, остальные девять добавляют остаток, а в целом жадный поиск воспроизводит качество ручного набора, но не превосходит его. Среди выбранных семейств есть те, которых нет в ручном наборе (доля органических прослушиваний пары пользователь-трек и трека), но их вклада для превосходства не хватило. Группы упорядочиваются по незаменимости. На первых местах стоят пара пользователь-артист (ΔAUC минус 0.0137), пара пользователь-трек (минус 0.0133) и статистики трека (минус 0.0106), затем статистики пользователя (минус 0.0064), артист и альбом (минус 0.0048), давность и возраст (минус 0.0036) и доля органических прослушиваний (минус 0.0034). Группы с эффектом около 0.001 AUC (события skip, число уникальных треков, окно 90 дней, отношения) лежат в пределах шума при единственном запуске, а удаление группы пользователь-альбом (минус 0.0002) не отличимо от нуля, то есть альбомные признаки полностью заменяются остальными.
 
Ранжирование и общая разделимость дают разные картины, и это различие важно. По NDCG@10 пара пользователь-трек (минус 0.0330) важнее пары пользователь-артист (минус 0.0158), хотя по AUC они равны: возможное объяснение состоит в том, что прямые повторные прослушивания помогают расставить треки внутри списка, а знание артиста помогает отделять положительные от отрицательных по всему списку (это не проверялось). На трудном протоколе соотношение обратное (NDCG@10 минус 0.0640 у пары пользователь-артист против минус 0.0430 у пары пользователь-трек): когда отрицательные взяты из любимых артистов, именно признаки привязанности к артисту дают разделение. Удаление отношений слегка снижает AUC (минус 0.0009), но заметно повышает Recall@10 (+0.0051 [+0.0009, +0.0093]), то есть отношения улучшают общую разделимость, а на верхушку списка влияют отрицательно; причина не выяснялась. Одиночный признак числа Listen+ пары пользователь-артист на трудном протоколе слабее (AUC 0.559 против 0.724), а вся группа важнее, поэтому вероятно, что важна степень привязанности, а не факт знакомства; прямого эксперимента нет.
 
Гипотеза, что вклад доли органических прослушиваний создан сэмплированием, проверялась разбиением группы на два подмножества (трудный протокол). Органичность трека, артиста и альбома дала минус 0.0002 [минус 0.0013, +0.0009], а органичность пользователя и пар минус 0.0021 [минус 0.0037, минус 0.0005]; гипотеза не подтвердилась, вклад принадлежит признакам вкуса пользователя.

### 4.7. Стоимость расчёта
 
Пул содержит в 3.6 раза больше спецификаций, чем ручной набор (487 против 134), но считается всего в 1.4 раза дольше (9.1 против 6.6 секунды на отсечку), потому что стоимость определяется числом проходов по истории (связки сущность и окно), а не числом агрегатов. Затухание ломает эту экономию: набор из 134 признаков с затуханием считается 18.4 секунды (в 2.8 раза дольше), 196 затухающих счётчиков 25.2 секунды, тогда как 42 тренда считаются за 0.7 секунды. Расчёт всех 487 признаков на 12 отсечках занял 58 секунд, обучение на них 101 секунду против 29 у ручного набора. Зависимость от числа пользователей не измерялась.
 
### 4.8. Абляция «ручной набор + группа» и её ограничения
 
Без изменений в числах; добавить сравнение с LOGO для групп, в которых оба метода согласуются, и тех, где расходятся. Согласуются доля органических прослушиваний (+0.0033 AUC при добавлении к ручному набору и минус 0.0034 при удалении из пула) и окно 90 дней (знак совпадает, но абсолютные значения +0.0029 и минус 0.0013 различаются вдвое). Расходятся группы событий skip (+0.0003 при добавлении и минус 0.0016 при удалении) и альбомные признаки (+0.0024 при добавлении и около нуля при удалении группы пользователь-альбом, но минус 0.0048 при удалении артиста и альбома вместе). Расхождение, вероятно, связано с тем, что при добавлении группа восполняет отсутствующую информацию, а при удалении оценивается только то, чего не хватает при наличии всех остальных признаков, то есть измеряются разные величины.

### 4.9. Ограничения и неподтверждённые результаты

**Не получилось / не подтвердилось:**

- жадный отбор не превзошёл ручной набор (интервалы разности содержат ноль) при затратах 1003 с;
- отбор по важности оставил весь пул (*k* = 487);
- окна, подобранные по данным, и сетка из 13 окон не отличимы от окон 1/7/30/all;
- затухающие счётчики и тренды не дали устойчивого прироста (максимум +0.0009 AUC, пограничный интервал);
- гипотеза об артефакте сэмплирования для frac_org не подтвердилась.

**Ограничения валидности:**

1. *Масштаб.* Использовано 2000 из 10 000 пользователей; статистики треков и артистов вычисляются по выборке. Масштабирование на 5000 и 10 000 пользователей не проверялось.
2. *Кандидаты.* Кандидаты сэмплируются, а не берутся с реального этапа отбора. Доля положительных треков, не встречавшихся до *T*, не измерена; абсолютные метрики могут быть завышены.
3. *Трудный протокол.* Один seed, без подбора гиперпараметров; эксперимент с окнами и жадный отбор не запускались.
4. *LOGO и абляции.* Один seed. Доверительные интервалы учитывают выборку пользователей, но не разброс обучения (около 0.0003 AUC).
5. *Множественные сравнения.* Приведены десятки интервалов по четырём метрикам без поправок; пограничные результаты не следует считать установленными.
6. *Порядок экспериментов.* Тест не использовался при выборе признаков, *k* и гиперпараметров, однако промежуточные тестовые значения наблюдались, и последующие эксперименты (окна, операторы, трудный протокол) спроектированы после них. Возможен небольшой оптимистичный сдвиг оценок.
7. *Объём исследования.* Один датасет, одна цель (Listen+ за сутки), один горизонт, одна модель (LightGBM). В оценку попадают только пользователи с хотя бы одним Listen+ в окне и историей не менее 50 событий.
8. *Данные.* События `unlike` и `undislike` не учитываются; смысл флага `is_organic` неоднозначен.
9. *Отбор.* Жадный отбор использует прокси-модель и AUC на уровне семейств; другие стратегии (например, обратное исключение) не исследовались.
10. *Другие направления* (графовые модели, модели над последовательностью событий) не исследовались; выводы относятся только к перебору признаков и отбору.
11. *Версии библиотек* при основных прогонах в Colab не фиксировались (`requirements.txt` задаёт только нижние границы), поэтому в третьем–четвёртом знаке значения могут отличаться.

## 5. Выводы

1. **Пул против ручного набора.** В равных условиях (одинаковые кандидаты, отсечки и бюджет подбора гиперпараметров) пул из 487 признаков превосходит ручной набор из 134 признаков по всем четырём метрикам на обоих протоколах кандидатов (95 % ДИ не содержат нуля). Лёгкий протокол: ΔAUC +0.0055, ΔNDCG@10 +0.0068. Трудный: ΔAUC +0.0060, ΔNDCG@10 +0.0144 (1 seed, без подбора гиперпараметров). Абсолютная величина прироста невелика.
2. **Способ отбора.** Преимущество дало расширение пространства признаков, а не усложнение поиска: отбор по важности сохранил весь пул, жадный отбор (1003 с) не отличим от ручного набора. Top-100 по важности превосходит ручной набор по AUC и LogLoss на обоих протоколах и в 2.6–3.2 раза быстрее обучается, чем пул; на лёгком протоколе незначительно уступает пулу (ΔAUC −0.0013).
3. **Выбор окон.** При заданной сетке разумных горизонтов точное значение окна влияет слабо: сетка из 13 окон (ΔAUC +0.0006 [−0.0004, +0.0015]) и окна, выбранные по важности, не отличимы от 1/7/30/all. Случайный набор окон хуже (ΔAUC −0.0057 [−0.0071, −0.0042]).
4. **Новые операторы.** Затухающие счётчики и тренды не дают устойчивого прироста (не более +0.0009 AUC, пограничный интервал) при увеличении времени обучения в 1.6–1.9 раза и времени расчёта признаков в 3.3 раза.
5. **Вклад групп.** Наибольшее снижение AUC при удалении наблюдается для признаков связи «пользователь—артист» (ΔAUC −0.0137 на лёгком и −0.0276 на трудном протоколе) и «пользователь—трек» (−0.0133 и −0.0148). Относительная важность групп зависит от способа формирования кандидатов.
6. **Применимость.** Результаты получены на одной выборке данных (2000 пользователей), одной модели и сэмплированных кандидатах; перенос на полный датасет и реальный этап отбора кандидатов не проверялся. Предлагаемые направления: проверка на 5000–10 000 пользователях, на кандидатах реального отбора, доведение трудного протокола до уровня лёгкого (подбор гиперпараметров, несколько seed), сравнение с графовыми моделями и моделями над последовательностью событий.

`run_experiments.py`, `run_stage2.py`, `run_windows.py`, `run_stage3.py`, `diagnostics.py`, `summarize.py` - эксперименты и сводки;
`inspect_data.py`, `colab_run.ipynb`, `run_all.sh` - проверка схемы данных, запуск в Colab, полный прогон;
`tests/test_leakage.py` - 8 тестов (отсечки не пересекаются; признаки не используют будущее, включая затухание и тренды; отрицательные не пересекаются с положительными и встречались до *T*; кандидаты перемешаны и детерминированы; bootstrap отличает хорошую модель от случайной, затухающий счётчик совпадает с расчётом на numpy);
`results/summary_easy.md`, `results/summary_hard.md`-сводки полученных результатов.

### 6.1. Окружение

Python 3.10 или выше. Пакеты (`requirements.txt`): `polars>=1.0`, `lightgbm>=4.0`, `scikit-learn`, `pyarrow`, `numpy`, `huggingface_hub`, `pytest`. Основные прогоны выполнены в Google Colab (CPU); версии библиотек там не фиксировались. Проверка кода выполнена позднее в окружении Python 3.13, polars 2.0.0, LightGBM 4.7.0, scikit-learn 1.9.1, numpy 2.5.3: тесты проходят, конвейер работает на синтетических данных; числа на реальных данных в этом окружении не пересчитывались.


### 6.2. Проверка без данных

```bash
pip install -r requirements.txt
python -m pytest -q tests        # 8 тестов, около 15 с
```

Тесты используют синтетические данные; числа на синтетике не сопоставимы с результатами статьи и служат только проверкой работоспособности конвейера.

### 6.3. Полный прогон

Общее время на CPU Colab при 2000 пользователях — по оценке 3–4 часа.

```bash
bash run_all.sh work 2000        # всё подряд

# по шагам (этап 1 запускается первым в каждой рабочей папке:
# остальные скрипты берут из его results.json конфигурацию и наборы признаков)
python run_experiments.py --n-users 2000 --work-dir work
python diagnostics.py --work-dir work
python run_stage2.py --work-dir work --seeds 3 --tune 6
python run_windows.py --work-dir work --seeds 3
python run_stage3.py --work-dir work --seeds 2
python summarize.py --work-dirs work

# трудный протокол кандидатов (161 кандидат на группу)
python run_experiments.py --n-users 2000 --work-dir work_hard \
       --neg-pop 50 --neg-hist 50 --neg-art 50 --skip-greedy
python diagnostics.py --work-dir work_hard
python run_stage3.py --work-dir work_hard --seeds 1 --quick --skip-timing
python summarize.py --work-dirs work work_hard
```

Кэш признаков: `work*/<tag>[__win|__ext]/*.parquet`. При изменении конфигурации кэш следует удалить; у `run_experiments.py` есть также флаг `--rebuild`. `summarize.py` собирает таблицы из JSON-файлов в `summary.md`, исключая ручной перенос чисел.

### 6.4. Контрольные значения после запуска

При успешном запуске ожидается выполнение условий
1. Все 8 тестов проходят.
2. В test ровно 1257 групп; 69 685 строк (лёгкий) и 202 017 строк (трудный); доля положительных 0.282 и 0.097. При других значениях кандидаты отличаются (возможная причина - версии polars или numpy; не проверялось).
3. Значения таблицы 1 должны быть близки к приведённым; точное совпадение ожидается только при тех же версиях библиотек. Два независимых запуска в одном окружении совпадают до 1e-16.
4. Знак и статистическая значимость разностей в таблице 2.

### 6.5. Приложение. Параметры и форматы результатов

| Параметр | Значение |
|---|---|
| LightGBM, по умолчанию | `objective=binary`, `metric=binary_logloss`, `learning_rate=0.05`, `num_leaves=63`, `min_data_in_leaf=50`, `feature_fraction=0.7`, `bagging_fraction=0.8`, `bagging_freq=1`, `lambda_l2=1.0`, `deterministic=True`, `force_row_wise=True` |
| Длина обучения | до 2000 деревьев, ранняя остановка 50 раундов по LogLoss на val |
| Прокси-модель жадного отбора | `learning_rate=0.1`, `num_leaves=31`, `min_data_in_leaf=50`, `feature_fraction=0.8`, bagging 0.8, 120 деревьев, до 300 000 строк train; 40 семейств в шорт-листе, не более 15 шагов, минимальный прирост AUC 0.0005 |
| Сетка подбора | `num_leaves` {15, 31, 63, 127}, `min_data_in_leaf` {20, 50, 100, 200}, `feature_fraction` {0.3, 0.5, 0.7, 0.9}, `lambda_l2` {0, 1, 10}; 6 случайных конфигураций + параметры по умолчанию |
| Конфигурация данных | `n_users=2000`, seed 0, горизонт 1 день, 6 train-отсечек с шагом 3 дня, 3 val, 3 test, порог Listen+ 50 %, `min_hist_events=50` |
| Кандидаты | популярные: окно 7 дней, вес count^0.75; артисты: топ-5 за 30 дней, вес count^0.75; лёгкий протокол 20/20/0, трудный 50/50/50 |
| Bootstrap | 300 ресемплов пользователей, 95 % процентильный интервал, seed 0 |
| Seed обучения | 0, 1, 2 (число задаётся флагом `--seeds`) |

Результаты каждого скрипта записываются в JSON в рабочей папке. В `methods` метрики имеют вид пары [среднее, разброс по seed], в блоках `bootstrap` - словарь `{diff, lo, hi, p_better}`.
